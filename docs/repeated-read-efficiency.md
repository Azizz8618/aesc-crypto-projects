# Методика подсчёта эффективности при сокращении повторного чтения данных

Документ задаёт порядок расчёта, по которому можно доказать, что метод из
[cost-optimization.md](cost-optimization.md) действительно снизил расход
при решении задачи, а не просто изменил форму отчёта. Методика опирается на
фактические замеры в [token-savings-stats.md](token-savings-stats.md) и на
проверки в смежном проекте `re-forex`.

## 1. Границы и определение

**Повторное чтение** — повторная подача в контекст агента тех же самых данных:
целого файла, листинга, трассы, лога прогона или журнала. Повтором считается
каждое чтение после первого, даже если оно делается другой командой.

Эффективность считается только при сохранении результата: контрольная сумма,
эталонная выдача или вердикт SIMH должны совпадать с базовым прогоном.
Экономия, полученная ценой непроверенного результата, не засчитывается.

Методика измеряет три слоя:

1. **Чтение источника** — сколько токенов израсходовано на повторную подачу
   одного и того же материала.
2. **Поток сессии** — сколько всего токенов и свежего ввода потрачено на задачу.
3. **Решение задачи** — затраты на единицу корректно решённой задачи.

## 2. Базовые величины

Для одного фиксированного источника (файл, лог, трасса) измеряются:

| Обозначение | Смысл | Как получить |
| --- | --- | --- |
| `s` | токены одного полного чтения источника | `tokcount <файл>` |
| `s'` | токены одного чтения замены (карта, сводка, извлечение) | `tokcount <карта>` или `printf ... \| tokcount -` |
| `q` | число чтений источника за задачу | счётчик вызовов чтения в журнале сессии |
| `R` | токены, потраченные на чтения: `R = q × s` | расчёт |
| `I, O, C_r, C_c` | свежий ввод, вывод, чтение кэша, создание кэша | `ccusage opencode daily --json` |
| `T` | суммарные токены: `T = I + O + C_r + C_c` | расчёт |
| `W` | время решения, с | секундомер прогона |
| `N` | число шагов агента (вызовов инструментов) | журнал сессии |
| `Q` | признак корректности: 1 — контроль пройден, 0 — нет | эталон / PASS |

Индексы `0` и `1` обозначают базовый прогон (до метода) и прогон с методом.

## 3. Метрики сокращения чтения

**Объём повторного чтения:**

```
R0 = q0 × s0        R1 = q1 × s1' + e0
```

где `e0` — токены неизбежного полного чтения (например, одно чтение файла
для правки конкретного диапазона).

**Абсолютная экономия:** `ΔR = R0 − R1`.

**Доля устранённого чтения:** `ηR = 100 × ΔR / R0`.

**Кратность сокращения:** `kR = R0 / R1`.

**Доля свежего ввода:** `f = 100 × I / T`; **доля чтения кэша:**
`c = 100 × C_r / T`; **множитель контекста:** `m = (I + C_r) / I`.

Последняя метрика показывает, во сколько раз больше контекста обрабатывается
на один свежий токен. В текущих сессиях `m = 40,48×` за 25.11 и `51,24×`
за весь период ([token-savings-stats.md](token-savings-stats.md)).

## 4. Метрика эффективности решения

Базовая метрика, если измерены только токены:

```
Эт = Q × T0 / T1
```

Расширенная метрика, если измерены время и число шагов:

```
Э = Q / (α·T1/T0 + β·W1/W0 + γ·N1/N0),   α + β + γ = 1
```

Рекомендуемые веса: `α = 0,5` (токены), `β = 0,3` (время), `γ = 0,2` (шаги).
Интерпретация: `Э > 1` — задача решена эффективнее, `Э = 1` — без изменений,
`Э < 1` — метод ухудшил решение. При `Q = 0` эффективность равна нулю независимо
от экономии токенов.

Отдельно фиксируется **эффективность чтения**: `Эч = Q × kR`. Она показывает,
во сколько раз дешевле стал доступ к тем же данным.

## 5. План A/B-проверки

1. Зафиксировать задачу и критерий приёмки: CONTROL SUM, `КОНЕЦ ЗАДАЧИ`,
   verdict `PASS`, побайтовая сверка.
2. Замерить базовый прогон: `q0`, `s0`, `W0`, `N0`, `Q0`, снимок `ccusage`.
3. Применить один метод M1–M15, не меняя критерий приёмки.
4. Заменить прогон: `q1`, `s1'`, `e0`, `W1`, `N1`, `Q1`, снимок `ccusage`.
5. Проверить `Q1 = Q0 = 1`. Если результат отличается — экономия не засчитывается.
6. Рассчитать `ΔR`, `ηR`, `kR`, `ΔT`, `Эт`, `Э`, `Эч`.
7. Записать оба прогона в таблицу ниже и приложить команды Measurements.

**Обязательные условия сравнения:** одна и та же модель, одинаковый начальный
контекст, одинаковая версия исходников и эталонов, одинаковый набор команд
проверки. Иначе разница в токенах объясняется не методом.

## 6. Измерение

Токены одного фрагмента:

```sh
tokcount <файл>
printf '%s\n' "$ТЕКСТ" | tokcount -
```

Снимок расхода до и после задачи:

```sh
ccusage opencode daily --json > /tmp/before.json
# ... решение задачи ...
ccusage opencode daily --json > /tmp/after.json
```

Минимальный расчёт дельты:

```python
import json, sys

def totals(path):
    d = json.load(open(path))
    rows = d.get('daily', d)
    return {k: sum(x[k] for x in rows) for k in (
        'inputTokens', 'outputTokens', 'cacheReadTokens', 'cacheCreationTokens')}

a, b = map(totals, sys.argv[1:3])
for k in a:
    print(f"{k:24} {a[k]:>14,} -> {b[k]:>14,}  delta={b[k]-a[k]:+,}")
t0, t1 = sum(a.values()), sum(b.values())
print(f"total                   {t0:>14,} -> {t1:>14,}")
print(f"сэкономлено             {100*(t0-t1)/t0:>14.2f}%   множитель {t0/t1:.2f}x")
```

Снимки должны покрывать один и тот же набор дат: `ccusage daily` группирует
по календарным суткам, поэтому для задачи внутри дня берите дельту одной
строки с нужной датой.

## 7. Рабочие примеры

### 7.1. Карта кода вместо полного файла (M7)

Измерено: `s0 = 23 954` токена, `s1' = 847` токенов. Пусть за задачу файл
читался 5 раз, а для правки один раз прочитан целиком:

```
R0 = 5 × 23 954        = 119 770
R1 = 5 × 847 + 23 954 =  28 189
ΔR = 91 581   ηR = 76,46 %   kR = 4,25×
Эч = 1 × 4,25 = 4,25   (при Q = 1)
```

Это расчётный пример на измеренных значениях `tokcount`; число чтений `q = 5`
задано условием примера, а не замером конкретной сессии.

### 7.2. Извлечение строк из доказательств (`re-forex`, docs/142)

Измерено: полный комплект доказательств `R0 = 16 938` токенов, извлечённые
решающие строки `R1 = 70` токенов. Вердикт SIMH A/B/PATCH/RESTORE — PASS,
значит `Q = 1`:

```
ΔR = 16 868   ηR = 99,59 %   kR = 241,97×   Эч = 241,97
```

В диалог попадает только извлечение, не полные `prn0`. Это образец для задач
трассировки и испытаний: экономия достигается без потери доказательности.

### 7.3. Фон текущих сессий

За 25.11: `I = 8 492 064`, `C_r = 335 279 360`, `T = 344 263 668`,
`c = 97,39 %`, `m = 40,48×`. Это не A/B-результат, а контекст, на фоне которого
следует оценивать новый метод: даже небольшое сокращение свежего ввода даёт большой
прирост множителя.

| Метрика | До метода | После метода | Изменение |
| --- | ---: | ---: | ---: |
| Чтений источника `q` | | | |
| Токенов чтения `R` | | | |
| Input `I` | | | |
| Output `O` | | | |
| Cache Read `C_r` | | | |
| Cache Create `C_c` | | | |
| Всего `T` | | | |
| Время `W`, с | | | |
| Шагов `N` | | | |

К отчёту прикладываются: команды `tokcount`, оба `ccusage`-снимка, контрольная
сумма или verdict и имя проверенного эталона.

## 9. Порог приёмки и чек-лист

1. `Q0 = Q1 = 1`: результат байт-в-байт совпадает с эталоном.
2. `ΔR > 0` и `ΔT > 0`: чтение и общий расход действительно сократились.
3. `ηR ≥ 30 %` для разовой правки или `kR ≥ 2×` для повторного чтения логов.
4. `W1 ≤ 1,10 × W0`: метод не должен ухудшать время решения более чем на 10 %.
5. `N1 ≤ N0`: число шагов не растёт без причины.
6. Описан один метод M1–M15, а не несколько сразу; иначе атрибуция экономии
   невозможна.
7. В отчёте указаны версии исходников, модели и дата снимков.

## 10. Ограничения

- `cacheRead` дешевле свежего ввода, но не бесплатен; сокращение токенов —
  прокси для нагрузки на контекст, а не точная денежная экономия.
- У бесплатных моделей цена в `ccusage` равна 0, поэтому стоимость считается
  как 0 при любом объёме; сравнивать нужно токены.
- `C_c = 0` в текущих сессиях: метод работает на уже прогретом кэше и не
  создаёт новый.
- `W` и `N` часто отсутствуют в журнале; тогда применяется базовая формула
  `Эт`, а расширенная метрика помечается как не измеренная.
- Проценты из `token-saver` и `code-map` — оценки методики; к фактическим
  относятся только замеры `tokcount` и `ccusage`.
