# Перенос изменений связками git bundle

Документ описывает «связку гит» — передачу изменений одним файлом-связкой
(`git bundle`) — как штатный способ обмена между рабочим хранилищем версий
среды и GitHub, а также между рабочими машинами. Дополнение к
[CONTRIBUTING.md](../CONTRIBUTING.md); ссылка на связку — обязательный
элемент сдачи задачи, выполняемой офлайн.

## 1. Зачем нужны связки

Рабочее место спецкурса не всегда связано с GitHub напрямую: хранилище
версий ведётся рядом с эмуляторными средами, а перенос данных идёт через
средства среды (тома, деки, обмен файлами). Связка git bundle решает эту
задачу: это один файл, содержащий объекты git и ссылки веток, который
можно перенести любым носителем и затем присоединить к репозиторию как
обычный источник.

Связки используются для:

- передачи коммитов с рабочей машины в репозиторий aesc-crypto-projects
  и в репозитории-инструменты (besm-crypto, dispak и другие);
- передачи обновлений из GitHub на рабочую машину без прямого доступа к
  сети;
- архивирования состояния работ на этапах плана (например, перед
  резервным копированием томов на этапе «Запись»).

## 2. Что передаётся связками, а что нет

Связки предназначены только для содержимого репозиториев: исходники
(БЕМШ, Паскаль), деки заданий, источники схем ДРАКОН, документы ЕСПД,
файлы этой документации.

Связками **не передаются**: образы томов и лент среды, ключевой файл,
база паролей, таблицы замен, персональные данные. Это согласуется с
правилами безопасности среды: ключи и таблицы замен хранятся только в
ключевом файле областей АРФА с паролем, а резервные копии томов —
отдельный процесс этапа «Запись» с побитовой сверкой.

## 3. Создание связки

Полная связка (все ветки и теги) — делается редко, обычно при
архивировании этапа:

```bash
git bundle create aesc-20261112-etap0-base.bundle --all
```

Инкрементальная связка — от общего с целевым репозиторием состояния:

```bash
git fetch origin main
git bundle create aesc-20261112-etap2-s48-draft.bundle origin/main..main
```

Именование: `aesc-ГГГГММДД-этап-N-кратко.bundle` — дата создания, номер
этапа по [STATUS.md](../STATUS.md), краткое назначение. Для связок в
репозитории-инструменты имя начинается с имени проекта, например
`dispak-20261115-overlay-loader.bundle`.

## 4. Проверка и приём связки

Проверка целостности до переноса и после него обязательна:

```bash
git bundle verify aesc-20261112-etap2-s48-draft.bundle
```

Приём в целевой клон — как в обычный удалённый источник:

```bash
git fetch aesc-20261112-etap2-s48-draft.bundle main:from-bundle
git log --oneline from-bundle
git checkout main && git merge from-bundle
```

Клонирование из полной связки (восстановление после сбоя или новая
рабочая машина):

```bash
git clone aesc-20261112-etap0-base.bundle aesc-crypto-projects
```

После приёма связка не удаляется: она лежит в хранилище версий рядом с
исходниками документов как фиксация состояния на дату.

## 5. Связки в цикле сдачи задачи

1. Работа выполняется в отдельной ветке с осмысленными коммитами.
2. Перед сдачей создаётся и проверяется (`git bundle verify`) связка.
3. Если изменение переносится офлайн, в задаче (issue) или запросе на
   включение изменений указывается: имя связки, контрольная сумма
   (`sha256sum`), диапазон коммитов. Шаблон запроса содержит
   соответствующий пункт чек-листа.
4. После включения изменения в основную ветку создаётся ответная связка
   `origin/main..main` для синхронизации рабочей машины.
5. Запись о связке попадает в журнал изменений [STATUS.md](../STATUS.md)
   вместе с записью о закрытой работе.

## 6. Контроль целостности

- `git bundle verify` перед отправкой и после приёма — обязательный
  минимум;
- контрольная сумма файла (`sha256sum`) фиксируется в задаче; приёмник
  сверяет сумму до приёма связки;
- при расхождении связка не применяется и перенаправляется на повторную
  выгрузку;
- раз в этап создаётся полная связка `--all` как точка восстановления;
  её имя заносится в журнал изменений STATUS.md.

## 7. Что делать при расхождении веток

Если рабочая машина и GitHub расходятся (оба продвинулись с общего
основания), создаются две инкрементальные связки — в каждую сторону — и
слияние выполняется на рабочей машине обычным `git merge` с последующей
отправкой объединённого состояния одной связкой. Конфликты слияния
разрешаются до связки: в связку попадает только проверенное состояние,
прошедшее регрессию (см. [CONTRIBUTING.md](../CONTRIBUTING.md), раздел
«Регрессия»).
