# Правила работы над репозиторием

Репозиторий координирует работы по плану внедрения блочного шифрования.
Правила описывают, как открывается задача, как она выполняется и в каком
виде сдаётся. Полная методология среды — в
[docs/methodology.md](docs/methodology.md); критерии приёмки — в
[docs/stages.md](docs/stages.md).

## 1. Цикл работы над задачей

Каждая задача проходит полный цикл; пропуск фазы считается браком.

1. **Открытие.** Задача заводится по шаблону «Задача этапа»
   (`.github/ISSUE_TEMPLATE/stage-task.md`) с указанием этапа
   [STATUS.md](STATUS.md), состава работ и критерия готовности.
2. **Проектирование.** Перед кодированием фиксируется решение: точка
   интеграции, состав модуля, ожидаемые затраты памяти (зоны). Для
   алгоритмов рисуется схема ДРАКОН.
3. **Кодирование.** Автокод БЕМШ или Паскаль 15.1; вызовы ОС — только
   штатными экстракодами (050, 063, 064, 070, 0157/0116).
4. **Оптимизация.** По листингам и замерам времени сокращаются команды
   цикла и объём памяти: плохая оптимизация не проходит ограничение ОЗУ
   на задачу.
5. **Проверка.** Прогон в эмуляторе dispak, сверка с эталонами байт в
   байт; системные изменения дополнительно проверяются на simh.
6. **Сдача.** Запрос на включение изменений по шаблону с заполненным
   чек-листом регрессии; если изменение готовится офлайн, к запросу
   прилагается связка git bundle
   ([docs/git-bundle.md](docs/git-bundle.md)).
7. **Документирование.** Изменения отражаются в соответствующем
   документе `docs/` и в [STATUS.md](STATUS.md) в тот же день.

## 2. Правила безопасности среды

- Изменение операционной среды выполняется только после резервной копии
  тома, проверенной чтением записи обратно.
- Изменения вносятся новыми модулями через список модулей и раскрой
  виртуальной памяти; переработка ядра не допускается.
- Целостность ОС ДИСПАК подтверждается побитовой сверкой зон; после
  записи модулей выполняется побайтовая сверка томов.
- Запись библиотек ведётся штатными средствами ПЕРСО: загрузчик
  Монитора-80 проверяет даты записей каталога.
- Таблицы замен, ключи и пароли не попадают в репозиторий и в выдачи;
  их место — ключевой файл в областях АРФА с паролем и монопольным
  захватом тома.

## 3. Регрессия

Перед закрытием задачи обязателен набор проверок, соответствующий
изменению:

| Изменение | Обязательная регрессия |
| --- | --- |
| Модуль шифрования (С48, ГОСТ, имитовставка) | Контрольные тест-векторы ([docs/stages.md](docs/stages.md), раздел 4) |
| Перехват обмена, паспорта задач | Цикл зоны задачей ОС на dispak; спорные случаи — на simh |
| Ключевое хозяйство | Цикл «пароль — запись — чтение» с базой тома 203; негативные случаи |
| Системные вызовы криптосервиса (шифрование области, смена ключа, опрос состояния) | Негативные случаи раздела 8 плана; отказ выдачи при несходстве имитовставки |
| Защита тома 2053 | Побайтовая сверка областей тома до и после включения шифрования; имитация отказа ключевого сервиса; режим открытого тома (признак в метке) |
| Расширение dispak (оверлеи, объектные файлы) | Прогон статических оверлеев Дубны со сверкой выдач с эталоном эмулятора Дубны |
| Любое изменение | Полный пакет dispak (51 испытание); выдачи сверяются байт в байт |
| Документация, схемы ДРАКОН | Регрессия конвейера: 31 случай СИПРОДа, эталоны ДРАКОНа |

Векторы шифра С48 после первой сборки не изменяются. Ошибка регрессии
оформляется по шаблону «Дефект» (`.github/ISSUE_TEMPLATE/defect.md`)
с указанием прогона, эталона и расхождения.

## 4. Связки git bundle

Перенос изменений между рабочим хранилищем версий и GitHub выполняется
связками (`git bundle`); полный регламент — в
[docs/git-bundle.md](docs/git-bundle.md). Короткие правила:

- в репозиторий и связки попадают исходники, деки, схемы ДРАКОН,
  документы и рабочий образ тома 2348 (`disks/2348`, см.
  [docs/disk-2348.md](docs/disk-2348.md)); остальные образы томов и лент,
  ключи, база паролей и таблицы замен не передаются;
- перед отправкой и после приёма связка проверяется командой
  `git bundle verify`; в задаче фиксируется контрольная сумма `sha256sum`;
- инкрементальная связка создаётся от общего состояния
  (`origin/main..main`), полная связка `--all` — точка восстановления,
  создаётся раз в этап и отмечается в журнале STATUS.md;
- слияние выполняется только после прохождения регрессии — в связку
  попадает проверенное состояние.

## 5. Работа с искусственным интеллектом

ИИ допускается как инструмент: разбор исходников re-dispak и
monitor80-re, черновые варианты модулей на БЕМШ и Паскале, поиск
неэффективных участков по листингам. Обязанности обучающегося:

- проверять каждый предложенный фрагмент по исходным текстам и прогону
  в эмуляторе;
- не принимать несуществующие команды автокода, экстракоды и механизмы
  ОС — «галлюцинации» отсеиваются сверкой с re-dispak и Монитором-80;
- уметь объяснить любое сданное решение на защите этапа.

## 6. Документация

- Документы выпускаются по ЕСПД: ГОСТ 19.201 (ТЗ), 19.404
  (пояснительная записка), 19.301 (программа и методика испытаний),
  19.502 (описание применения), 19.503 (руководство оператора).
- Блок-схемы набираются источниками ДРАКОН; исходники документов
  хранятся в хранилище версий рядом с текстами модулей.
- Правки документации проходят тем же запросом на включение изменений,
  что и соответствующий код или материал.
