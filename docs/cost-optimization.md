# Оптимизация расходов по профильным направлениям проекта

Документ описывает, как снижать расход токенов и повторное чтение кэша при
отладке, трассировке, испытаниях и сопровождении изделий учебно-экспериментальной
среды БЭСМ-6. Он дополняет [methodology.md](methodology.md),
[emulator-workflow.md](emulator-workflow.md) и [stages.md](stages.md): там описано,
*что* делается, здесь: как делать так, чтобы объём материала в контексте агента
оставался минимальным, а результат был воспроизводимым.

Пути смежных проектов ниже указаны относительно `~/Yandex.Disk`, если не
оговорено иное.

## 0. Исходные данные и цель

Зафиксированный пиковый суточный расход:

| Категория | Токенов | Доля от суммы |
| --- | ---: | ---: |
| Input | 60 478 832 | 1,687 % |
| Output | 3 548 848 | 0,099 % |
| Cache Create | 0 | 0 % |
| Cache Read | 3 521 333 120 | 98,214 % |
| **Итого** | **3 585 360 800** | 100 % |

Итог и проценты исправлены 25.11.2026 по данным `ccusage opencode daily --json`:
сумма четырёх компонентов за 24.11 равна 3 585 360 800; прежняя запись
3 589 602 251 расходилась с компонентами на 4 241 451 токен, а доля кэша
была занижена (98,100 % вместо 98,214 %).

Вывод: главный резерв экономии не в укорачивании ответов, а в сокращении
повторной загрузки контекста из кэша. `Cache Create = 0` дополнительно означает,
что новый кэш в этом контуре не создаётся, поэтому каждый цикл чтения больших
файлов и журналов оплачивается как чтение кэша. Цель методов ниже: уменьшить
объём попадающего в контекст материала, исключить повторные чтения, вынести
массивный поиск в изолированный контекст и измерять результат до и после.
Порядок расчёта эффективности при сокращении повторного чтения — в
[repeated-read-efficiency.md](repeated-read-efficiency.md).

## 1. Профильные направления и точки расхода

| Код | Направление | Этапы | Типовой источник расхода |
| --- | --- | --- | --- |
| D1 | Отладка задач в `dispak` | 4 | поинструкционные трассы `-tt`, дампы `BESM6_DD_DEBUG`, полные листинги |
| D2 | Системные прогоны в `simh` и СВС | 3, 6 | полный `set cpu debug`, загрузочные трассы, вывод всех устройств |

| D5 | Документация ЕСПД и память проекта | 1, 7 | повторное чтение одних и тех же `.md`, журналов и summaries |
| D6 | Метрология расходов | все | отсутствие измерения до и после изменений |

## 2. Перечень методов

### D1. Отладка задач в dispak

**M1. Наблюдаемая ячейка вместо полной трассы.**
Переменные `BESM6_WATCH` и `BESM6_WATCH_RW` дают только обращения к нужному
адресу, без поинструкционного потока (`dispak/dispak/cu.c:478-490`):

```sh
BESM6_WATCH=01167 BESM6_WATCH_RW=1 dispak -l JOB.b6
```

Эффект по наблюдениям проекта `re-bemsh`: адрес `012000` дал 5 строк,
`076505` дал 244 обращения, а полная трасса `-t 2` в том же прогоне составила
5 142 464 строки. Watchpoint не требует `BESM6_DD_DEBUG`.

**M2. Минимально достаточный уровень трассировки.**
Порядок перехода: `dispak -t JOB` (только экстракоды), затем `dispak -b JOB` с
командами отладчика `trace`, `breakpoint`, `where`, `step`, и только потом
`dispak -tt JOB` (каждая исполненная команда). Флаги описаны в
`dispak/dispak/dispak.c:23-27,165-167` и `re-bemsh/docs/DYNAMIC-TRACE.md:15-50`.
`BESM6_DD_DEBUG=1` включается фактом существования переменной и добавил всего
250 строк `DD pc=` в упомянутом прогоне, но дампы Э70/Э50/Э62 доступны только
для локальной сборки. Хуки `BESM6_CORE_ON_PC`, `BESM6_MTR_*`, `BESM6_AOX17_LOG`
в установленный `/usr/local/bin/dispak` не входят.

**M3. Поток трассы в агрегатор, а не в диалог.**
Трасса никогда не вставляется в запрос целиком. Она направляется в файл и
сразу сжимается в сводку (`re-bemsh/docs/DYNAMIC-TRACE.md:85-96`):

```sh
dispak -l -tt TRACE-listing.b6 2>&1 >listing-dynamic.txt \
  | python3 agg-dynamic.py >zones-dynamic.txt
```

На смеси 735 270 команд агрегатор оставил 3 099 уникальных адресов в 11 зонах
(`re-bemsh/docs/DYNAMIC-TRACE.md:114-135`). Готовые анализаторы:
`re-bemsh/tools/rvs_trace.py TRACE --catalog z0001.txt --format json --check`
(читает файл построчно, не загружая в память), `simh/BESM6/scripts/trace_zones.sh
<file> --summary | --unique | --zone 0677`, `re-dispak/trace_analyze.pl`,
`besm6-new/besm6.net/tools/diff_trace.py` (останавливается на первом
архитектурном расхождении). В диалог попадают `tail -40` или сводка.

**M4. Краткая нотация разбора трассы.**
По навыку `dispak-tracer` результат анализа трассы выводится как
`[ЗОНА:СМЕЩ] КОММЕНТАРИЙ`; полная таблица с ИР, кодом, адресом и зоной
выдаётся только по явному запросу. Одинаковые операции группируются, их
расшифровка не повторяется.

### D2. Системные прогоны в simh и СВС

**M5. Категории device debug и окна адресов.**
Вместо `set cpu debug` используются узкие категории и окно
(`simh/BESM6/README/README.md:555-566`, `simh/SVS/Tracing.md:46-84`):

```text
set md0 debug=OPS
set cpu0 debug=extra
set cpu0 window=76000:77777
set cpu0 nodebug=fetch
```

`debug=extra` даёт дешёвый call-trace, одна строка на экстракод. Флаг `FETCH`
примерно удваивает число строк. Разделитель флагов это `;`, а не запятая.
Трассу пишут в файл до включения отладки: `set debug -n out.trace`, затем
`set console log=log.txt`. Порядок важен: нельзя одновременно указывать
`set console log=X` и `set debug X`, это создаёт два буфера и рвёт вывод.

**M6. Точка останова вместо пошагового прохода.**
Полная трасса simh стоит около 3 МБ/с, загрузка в 20 млн команд даёт около 1 ГБ
(`simh/SVS/Tracing.md:245-260`). Вместо неё:

```text
set debug -n out.trace
br 33543
go 30036
```

`simh/SVS/runsim.sh:3-13` ограничивает прогон 5 ГБ и 300 с и сохраняет только
32 МБ начала и конца трассы. Для графического экстракода
`simh/BESM6/tests/run-gp-star.py:98-103,211-219` включает `set cpu debug`, но
печатает лишь отфильтрованные строки и последние 40 строк файла.

### D3. Статический анализ исходников и бинарников

**M7. Карта кода вместо полного файла.**
Все файлы C/C++ длиной более 500 строк открываются через карту
`~/.claude/skills/code-map` и скрипт `~/.cline/scripts/gen_code_map.sh`:

```sh
~/.cline/scripts/gen_code_map.sh --check besm6_cpu.c
test besm6_cpu.c -nt .cline/maps/besm6_cpu.c.map && echo "КАРТА УСТАРЕЛА"
```

Измерено 25.11.2026 на `simh/BESM6/besm6_cpu.c`: полный файл 2143 строки,
23 954 токена; карта 58 строк, 847 токенов; сжатие 28,3 раза, экономия
23 107 токенов на одном чтении. До перегенерации карты то же измерение давало
62 строки, 996 токенов и сжатие 24,1 раза; обе цифры верны для своих версий
карты. Карта хранится в `.cline/maps/<file>.map`, полное чтение остаётся
только для правки конкретного диапазона.

**M8. Поиск и чтение диапазона вместо чтения файла.**
`rg -n <symbol> <path>` находит нужный символ, после чего читается только
нужный диапазон строк. Вызовы группируются в одно сообщение, уже прочитанные
файлы не перечитываются. Оценки навыка `token-saver` для группировки вызовов
30-50 %, для поиска вместо чтения 40-60 %, для ограничения строк 20-40 %.
Это оценки методики, а не измерение данного проекта.

**M9. Персистентный хэш-кэш символов.**
`~/.cline/cache/hashes.md5`, `symbols.json`, `session_summary.md`,
`compression.log`. Если MD5 файла совпадает с сохранённым, берётся ранее
извлечённый набор символов, а не содержимое файла. По состоянию проверки кэш
содержит только заголовки и пустой объект `symbols.json`, то есть механизм
ещё не накопил данные и должен заполняться в ходе работ.

**M10. Выборочная трассировка СИПРОДа.**
`re-siprod/tools/siprod_trace.py SCHEMA --kind ЧИСЛА --ctx 8 --only ПОДСТРОКА`
печатает только обращения к данным заданного модуля с контекстом, вместо
полного листинга. Для дизассемблирования и поразрядной сверки используются
уже установленные `disbesm6` и `dtran` со скриптом `dtran/verify_dtran.pl`.

### D4. Регрессия и испытания

**M11. Сначала узкий прогон, затем полный контур.**
При правке одного модуля: `cd dispak/build && ctest -V -R <name>`, затем только
затронутые контрольные примеры. Полный набор 51 случай dispak, 31 случай
СИПРОДа и регрессия `re-dispak` запускаются один раз при приёмке
(`stages.md:100-136`). Логи не переносятся в диалог целиком: хэши зон, `cmp`
и `diff_trace.py` дают короткий доказательный результат. Критерий приёмки
остаётся прежним: сообщение «КОНЕЦ ЗАДАЧИ» без ошибок, выдачи совпадают байт в
байт, побайтовая сверка томов.

**M12. Сравнение вместо перечитывания.**
Для проверки зон и выдач используются `sha256sum`, `cmp -l` и первое расхождение
из `diff_trace.py`. Повторное чтение исходных файлов для подтверждения того же
результата запрещено: результат фиксируется один раз в протоколе.

### D5. Документация ЕСПД и память проекта

**M13. Изолированный поиск и краткие checkpoint-ы.**
Широкий поиск по многим проектам поручается read-only подзадаче с точным
вопросом, путями и требуемым форматом ответа, например таблицей доказательств.
В основной контекст возвращается только сводка. При достижении 40-60 тысяч
токенов summary сжимается, 60-80 тысяч требуется агрессивное сжатие, выше
80 тысяч перезапуск с self-summary. Локальные пороги
`~/.cline/scripts/auto-compact.sh`: компакция при 75-80 % от 128 тысяч,
предупреждение при файле сессии более 1 МБ.
`~/.cline/scripts/cleanup-logs.sh` архивирует логи более 50 МБ, хранит 7 дней
и удаляет архивы старше 30 дней.

**M14. Не читать один и тот же документ дважды.**
Факты из `README.md`, `STATUS.md`, `docs/*.md` и `MEMORY.md` фиксируются в
кратком summary с указанием пути и номера строки. Повторное обращение идёт к
summary, а не к полному тексту.

### D6. Метрология расходов

**M15. Измерение до и после.**
Перед отправкой большого фрагмента:

```sh
tokcount <file1> <file2>
printf '%s\n' "$TEXT" | tokcount -
```

Фактический расход по сессиям и моделям:

```sh
ccusage daily
ccusage opencode daily --json
```

`ccusage opencode daily --json` в этой среде вернул данные, например для
2026-10-09: cacheReadTokens 7 413 577, cacheCreationTokens 0. Метрика
доступна и может использоваться как контрольный показатель. Целевой результат:
снижение доли Cache Read при неизменном объёме приёмочных прогонов.

## 3. Обязательные правила

1. Не открывать файл более 500 строк без карты и без поиска нужного диапазона.
2. Не вставлять сырую трассу в запрос: только агрегат, сводка или `tail -40`.
3. Включать трассировку с самого узкого уровня и расширять только по причине.
4. Не перечитывать уже прочитанный файл в той же сессии.
5. Группировать независимые чтения и поиски в одно сообщение.
6. Выносить широкую разведку по нескольким проектам в подзадачу.
7. Подтверждать изменения хэшем или первым расхождением, а не повторным чтением.
8. Компактировать сессию до 75-80 % заполнения, не доводить до критического уровня.
9. Измерять токены до отправки и сверяться с фактическим расходом раз в неделю.
10. Сохранять критерии приёмки и побайтовую сверку в неприкосновенности:
    экономия токенов не может заменять испытания.

## 6. Ограничения и оговорки

- Проценты экономии в `token-saver` и `code-map` являются оценками методики.
  Прямо измерено в этом документе только сжатие `besm6_cpu.c` (28,3 раза
  после перегенерации карты 25.11) и доли категорий расхода.
- `agg-dynamic.py` упоминается в документации `re-bemsh`, но в дереве проекта
  отсутствует. Перед применением M3 нужно проверить наличие скрипта или
  использовать `rvs_trace.py`, `trace_zones.sh`, `trace_analyze.pl`.
- Хуки трассировки `BESM6_CORE_ON_PC`, `BESM6_MTR_*`, `BESM6_AOX17_LOG` требуют
  локальной сборки dispak и недоступны в установленном бинарнике.
- В `simh/BESM6/demo/dispak.ini:48-57,71-100` есть неразрешённые маркеры
  конфликта слияния, файл следует проверять перед прогоном.
- Карты кода в репозитории `simh` являются отслеживаемыми файлами. Регенерация
  меняет рабочее дерево, поэтому M7 применяется с `--check`, а измерение для
  одного файла снимается без сохранения изменения в репозитории.
- `ctest -N` показывает 52 теста `dispak`, документация называет 51.
- Навыки `token-saver`, `code-map` и скрипты `~/.cline` изначально созданы под
  Cline. В OpenCode и Claude Code используются те же принципы, а названия
  инструментов заменяются на эквиваленты текущей среды.
- Экономия контекста не отменяет контроль результата: каждый фрагмент,
  предложенный ИИ, проверяется по исходникам, прогону и побайтовой сверке
  согласно [methodology.md](methodology.md), раздел 4.

## 8. Активный контроль чтения: фаза A

Правила раздела 3 выполняются агентом добровольно. Чтобы сделать
их заметными, установлен локальный плагин OpenCode V2. Он **не перехватывает
промпты**, не меняет модели и не блокирует инструменты.

| Элемент | Путь |
| --- | --- |
| Плагин | `.opencode/plugins/token-guard/index.ts` |
| Конфигурация | `.opencode/plugins/token-guard/config.json` |
| Журнал | `.localdocs/token-guard.log` |
| Исключения Git | `.git/info/exclude` записи `.opencode/` и `.localdocs/` |

Механизм:

1. `ctx.tool.hook("execute.before")` смотрит только вызовы `read`.
2. Проверяется, что путь входит в один из корней из `config.json`, расширение
   из списка `.c`, `.h`, `.cc`, `.cpp`, `.be`, `.mad`, `.lst`, `.pas` и число
   строк больше порога `500`.
3. При срабатывании в журнал пишется предупреждение с путём карты
   `.cline/maps/<file>.map`, а на следующий вызов модели через
   `ctx.session.hook("context")` добавляется короткое напоминание.
4. Чтение продолжается обычным образом. Подмена пути и запрет пока не используются.

Список корней намеренно шире одного каталога проекта: `aesc-crypto-projects`,
`simh`, `dispak`, `re-dispak`, `re-bemsh`, `dtran`. Именно в смежных
репозиториях лежат тяжёлые исходники, например `simh/BESM6/besm6_cpu.c`.

Проверка фазы A (фактический вывод журнала):

```text
START projectRoot=/home/azizz/Yandex.Disk/aesc-crypto-projects threshold=500
/home/azizz/Yandex.Disk/simh/BESM6/besm6_cpu.c: 2143 строк.
Используйте карту /home/azizz/Yandex.Disk/simh/BESM6/.cline/maps/besm6_cpu.c.map и диапазон строк.
```

Загрузка плагина подтверждена в серверном журнале OpenCode записью
`loading plugin id=.../.opencode/plugins/token-guard`.

Управление:

- отключить без удаления: `"enabled": false` в `config.json`;
- изменить порог или список корней: те же поля `config.json`;
- удалить полностью: удалить каталог `.opencode/plugins/token-guard`.

**Фаза B не включена.** После недели наблюдения за журналом планируется добавить
мягкую подмену: если карта существует и свежая, путь чтения заменяется на карту.
Полный файл остаётся доступным явным запросом и через shell. Жёсткий запрет
чтения и бюджетный предохранитель в план не входят.
